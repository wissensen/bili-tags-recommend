# 后端接入与上线方案

## 当前结论

前端页面、状态切换和接口调用流程已经完整，生产构建可通过。现有六个 Route Handler 仍是待实现接口，因此目前不能保存真实稿件、上传真实视频或执行真实分析。

MVP 已确认以下边界：不做登录、只保留一个线上环境、提交仅保存为本项目内部记录、与 Bilibili 的内部依赖或接口完全无关；分析使用外部模型团队的接口，但该接口尚未提供。

现阶段不接入 R2，也不把视频持久化到云端。页面只读取浏览器本地文件并保存文件元数据；拿到模型接口后，优先让模型侧提供上传接口或短期文件地址，避免本项目为一次分析长期保存大视频。若将来明确要求保留原视频，再单独选择对象存储并评估费用。

零信用卡部署推荐采用一个 Cloudflare Worker：Next.js 页面改为静态导出并作为 Worker Static Assets 发布，`/api/*` 由同一个轻量 Worker 处理并直接绑定 D1。当前页面本身是客户端组件，不需要为它部署完整的 Next.js SSR/OpenNext 运行时。这能使用免费的 `workers.dev` 默认域名，并更容易控制在 Workers Free 的 CPU 和 bundle 限制内。免费额度与替代存储的官方核查见 `docs/free-mvp-hosting-research.md`。

## 数据模型

初始迁移位于 `migrations/0001_initial.sql`，包含：

- `upload_assets`：视频/封面元数据；MVP 可使用 `local_only` 状态且不填写 `object_key`。
- `analysis_jobs`：异步分析任务及失败信息。
- `recommendation_sessions`：一次分析生成的稳定候选快照。
- `submissions`、`submission_tags`：稿件与有序标签。
- `idempotency_keys`：分析和提交接口的幂等结果。

暂时无需登录，但不能完全取消请求隔离。服务端生成随机访客 ID，写入签名的 HttpOnly Cookie，并将其作为 `owner_id`；它不代表真实身份，只用于防止不同访问者读取或修改彼此的资源。所有业务查询仍必须同时校验 `owner_id`，不能只依赖客户端传入的资源 ID。

## 接口实现前置准备

| 接口 | 实现前必须准备 | 核心实现 |
| --- | --- | --- |
| `POST /api/uploads/init` | 签名访客 Cookie、速率限制、文件类型/大小规则 | MVP 只写入 `upload_assets(local_only)` 并返回 ID；模型接口明确后再决定由谁接收文件 |
| `POST /api/uploads/:id/complete` | 访客所有权校验、模型侧上传协议 | 当前可合并为元数据确认；有对象存储后才执行 HEAD、文件头和 ETag 校验 |
| `POST /api/analyses` | 分区字典、模型接口协议、幂等键 | MVP 可先使用基于标题和分区的确定性规则推荐器；模型接口就绪后替换为 HTTP Provider，再视其同步/异步协议决定是否创建任务 |
| `GET /api/analyses/:id` | 状态机、轮询间隔、超时与重试策略、错误码约定 | 按所有者读取任务；返回 `queued/running/succeeded/failed`，成功时返回 session ID |
| `POST /api/tags/recommend` | 标签词库、审核规则、排序特征、候选快照格式、cursor 签名密钥 | 从稳定候选快照分页，排除已选/重复项，签发不透明 cursor，不在请求间重新生成候选集 |
| `POST /api/submissions` | 签名访客 Cookie、标签规范化/上限/敏感词规则、幂等键 | 在事务中写入内部稿件和有序标签，返回内部提交编号；不调用任何外部发布平台 |

## 分析流水线前置准备

1. 让模型团队明确请求协议：直接文件、分片上传还是短期 URL，以及标题、分区、语言和最大时长等输入。
2. 确定抽帧与音频策略：抽帧间隔、关键帧数量、音轨格式和临时文件生命周期。
3. 由模型团队说明其 ASR、OCR、视觉理解能力，以及中国大陆可用性、费用、限流和数据合规要求。
4. 定义统一的分析结果 JSON Schema，包括主题、实体、候选标签、置信度、解释和模型版本。
5. 准备标签词库、分区映射、敏感词/禁用标签、热度与粉丝偏好数据；当前页面里的展示徽标不能由模型随意生成。
6. 模型接口提供后，再根据其同步/异步模式建立任务超时、最多重试次数、告警和人工重跑入口；当前不需要提前创建 Queue。

## 前端与真实接口联调时必须替换的三点

1. 接入模型团队最终提供的文件传输方式，并用真实上传事件显示进度。
2. 分析页按服务端 `pollAfterMs` 轮询，处理 `queued/running/failed`，不能只查询一次。
3. MVP 若只保存内部记录，可以暂不保存封面文件；浏览器 `blob:` URL 只用于当前页面预览。

## 部署顺序

1. 只创建一个线上数据库和一个线上应用，不创建预发、R2 或 Queue。
2. 应用 migration，配置签名访客 Cookie、Turnstile（或等价的人机校验）和写接口速率限制。
3. 将页面改为静态导出，把 Route Handler 迁移为同域 Worker API，并实现 D1 内部提交持久化。
4. 部署一个 Worker，使用免费的 `workers.dev` 默认域名即可；模型接口未配置时使用规则推荐器，不宣称已经执行真实视频理解。
5. 跑匿名访问隔离、重复提交、恶意刷写、数据清理和基本端到端测试。
6. 模型接口提供后再增加真实文件传输、分析任务和错误恢复，不提前建设用不到的基础设施。

## 已确认的 MVP 决策

- 不登录；使用匿名访客隔离和防刷措施。
- 只部署一个线上环境并使用平台默认域名。
- 视频分析调用模型团队接口，当前接口尚未提供。
- “发布成功”只表示内部稿件保存成功。
- 项目不使用任何 Bilibili 内部依赖或接口。

## 仍需确认

- 采用哪一个无需信用卡的免费托管与数据库平台。
- 匿名稿件保留期限，以及是否允许定期自动清理。
- 模型接口的文件传输协议、鉴权、限流、超时和返回 Schema。
